# 03 · Staged assistant architecture

Português: [README.pt-BR.md](README.pt-BR.md)

A People Analytics assistant that answers each question at the **cheapest stage that works** and only calls an LLM when it must. It runs **without network or API key**: the LLM is a pluggable function and the example uses stand-ins (`stubs.py`).

It reads the synthetic Gold of [project 02](../02-etl-consolidation-pattern), the only layer an agent should see.

> **Language note.** The sample assistant understands and answers in **Portuguese** (keywords, month names and answer strings). The architecture is language-independent. Supporting English means adding a language pack: keyword lists, month names and answer strings.

## The stages

| Stage | What it does | Calls an LLM? | Example (in Portuguese) |
|---|---|---|---|
| 0 | Direct pandas lookup: metric + company + month | No | "Qual o headcount da Acme Pay em março?" |
| 0.5 | Period parser. A month outside the series is answered immediately | No | "Headcount em janeiro de 2024" |
| 1 | Filtered, size-limited context sent to the LLM | Yes | "Explique a variação do turnover" |
| 2 | The LLM writes analysis code; the code is validated and run in a sandbox | Yes | "Ranking de turnover por empresa" |
| 3 | Controlled fallback | No | "Qual a capital da França?" |

```
question ─► metric without a source? ─► answers "not available"          (never escalates)
         ─► period outside the series? ─► answers "outside the series"   (never escalates)
         ─► lookup ─► stage 0
         ─► ranking/average ─► stage 2 ─► (failed?) stage 1
         ─► explain/summarize ─► stage 1
         ─► anything else ─► stage 3
```

## How to run

Requires the Gold generated by project 02:

```bash
py synthetic-data/generate.py
py projects/02-etl-consolidation-pattern/src/consolidate.py
py projects/02-etl-consolidation-pattern/src/build_gold.py

```

## Evaluation set result

18 questions in [eval_questions.csv](eval_questions.csv), each with an expected stage and an expected text snippet.

| Stage | Questions |
|---|---|
| 0 (lookup) | 11 |
| 0.5 (period) | 1 |
| 1 (LLM with context) | 2 |
| 2 (generated code) | 3 |
| 3 (fallback) | 1 |

13 of 18 were resolved with **no LLM call at all**. The 16 unit tests and the 18 questions pass.

**How to read this number:** the questions were written together with the router, and the LLM is a stand-in. The evaluation shows that the **routing** behaves as designed, not that a real model answers well. With a real model, the distribution would depend on the questions its users ask.

## Golden rules

1. **An indicator without a source never escalates.** An LLM would fill the gap with something plausible. The answer is "not available in the current sources".
2. **A month outside the series never escalates.** The parser resolves it at no cost.
3. **A value suppressed by k-anonymity is not reconstructed.** The answer is "not disclosed due to group size". The tests check that the LLM call counter stays at zero in these cases.
4. **The LLM only sees filtered context.** One or more companies and the last 6 months of the relevant table, truncated to 1,500 characters, never the whole Gold.
5. **Generated code is auditable.** A stage 2 answer keeps the code that ran.
6. **No credentials in the code.** The LLM is `llm(prompt) -> str`. In real use, read the key from an environment variable.

## Plugging in a real model

```python
import os
from assistant import answer, load_tables

def llm(prompt: str) -> str:
    key = os.environ["LLM_API_KEY"]  # never commit this
    ...                              # call the provider you use and return the text

print(answer("Explique o turnover da Acme Retail", load_tables(), llm=llm).text)
```

The same applies to `codegen(question, schema) -> str`, which must return code that assigns a `result` variable.

## Known limitations

- **Routing is keyword and regular-expression based.** It is cheap and predictable, but brittle with phrasing outside the pattern. A small classifier, or an LLM used only to route, would be the next step.
- **The sandbox is not a security boundary.** It blocks imports, private attributes, file writes and dangerous functions, but does not limit time or memory. In production, run generated code in an isolated process or container.
- **Generated analyses can silently drop suppressed months.** The example's turnover ranking is the average of the non-suppressed months. That is a methodological choice the answer does not state.
- **The period parser understands month and year.** Quarter and fiscal year are not implemented.
- **"Headcount" here is core contracts only (CLT and PJ)**, following the standardized file from project 02.

## What the assistant revealed while building it

When answering "time to hire", it returned `dez/2026` (December 2026), after the end of the series. The problem was not the assistant: the synthetic data generator let requisitions close in the future. An assistant that states the month it used exposes data defects. I fixed the generator, and the assistant now defaults to the last month of the **whole series**, not the last of each table.

## Structure

```
src/periods.py     stage 0.5: period parser
src/sandbox.py     stage 2: validation and execution of generated code
src/assistant.py   router and stages 0, 1, 2 and 3
src/stubs.py       fake LLM and code generator, to run offline
src/evaluate.py    measures stage per question and LLM calls
tests/             16 tests of the golden rules, with in-memory tables
eval_questions.csv evaluation set
```
