# 04 · SQL analytics layer

Português: [README.pt-BR.md](README.pt-BR.md)

The same Gold, queried with **SQL** instead of pandas. [DuckDB](https://duckdb.org) runs inside Python (no server, no network, no credentials), loads the Gold spreadsheets of [project 02](../02-etl-consolidation-pattern) and exposes them through governed views.

```
out/gold/*.xlsx  ──►  gold.*        raw copies of the Gold tables (suppressed cells are NULL)
                         │  sql/views.sql
                         ▼
                      analytics.*   governed views: the only schema a consumer queries
                         │  sql/queries/*.sql
                         ▼
                      named, versioned queries (ranking, trend, rolling average, privacy audit)
```

## How to run

Requires the Gold generated by project 02:

```bash
py synthetic-data/generate.py
py projects/02-etl-consolidation-pattern/src/consolidate.py
py projects/02-etl-consolidation-pattern/src/build_gold.py
py projects/04-sql-analytics-layer/src/warehouse.py                  # lists the stored queries
py projects/04-sql-analytics-layer/src/warehouse.py turnover_ranking
py projects/04-sql-analytics-layer/src/warehouse.py privacy_audit    # exit code 1 if any cell breaks k-anonymity
```

## Stored queries

| Query | What it shows | SQL technique |
|---|---|---|
| `turnover_ranking` | Latest published monthly turnover per company, ranked | CTE + `QUALIFY` + `rank()` |
| `headcount_trend` | Last 3 months of headcount and month-over-month change | `LAG()`, `QUALIFY` |
| `turnover_rolling` | Rolling 3-month turnover, only where at least 2 months were published | window frame `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` |
| `privacy_audit` | Every published cell that breaks the k-anonymity rule (must be empty) | `UNION ALL` of rules, one per Gold table |

## Design decisions

1. **Consumers query `analytics.*`, never `gold.*`.** The views are the contract. A table can change underneath without breaking a dashboard or an agent.
2. **Suppressed cells are NULL, and aggregates ignore NULL.** A hidden value is never averaged as zero or reconstructed. The rolling view also returns `months_with_data`, so a thin average looks thin.
3. **A company with nothing published does not appear in a ranking.** There is nothing to rank, and the query never invents a value.
4. **Privacy is audited in SQL.** `analytics.privacy_violations` re-checks the thresholds of project 02 (k = 3 and k = 5) against the published tables and also flags a row marked as suppressed that still carries a value. It is a second line of defense: the first is `build_gold.py`.
5. **Only stored queries run from the command line.** The name is looked up in a fixed list, so no file path or free SQL can be passed in.

## A mistake the tests caught

My first version of the ranking put `rank()` and `QUALIFY row_number() = 1` in the same `SELECT`. The window runs *before* `QUALIFY`, so it ranked every month of every company and the positions came out as 1, 3, 5, 12. The fix is to pick each company's latest month in a CTE first and rank afterwards. A test now checks that positions have no gaps.

## Known limitations

- **The tables are reloaded from the spreadsheets on every run.** Fine for a few hundred rows. At real volume, the Gold would be written straight to Parquet or to a database.
- **The audit mirrors the thresholds of project 02 by hand.** If `K_DEFAULT` changes there, `views.sql` must change too. A shared configuration would remove that duplication.
- **It audits the counts the pipeline promises to protect** (headcount, exits, closed requisitions, voluntary exits). Derived columns such as the number of women in a cut are not audited.
- **Not connected to the assistant of project 03 yet.** The assistant still reads the spreadsheets with pandas.
